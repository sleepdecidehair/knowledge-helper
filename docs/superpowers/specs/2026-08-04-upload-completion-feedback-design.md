# 文件上传完成反馈设计

## 目标

为知识库上传区增加可核对的文件上传反馈：用户选择文件后立即看到包含文件名、文件大小、进度条和状态的临时记录；成功时状态由“上传中”切换为“可用”，随后通过短动画并入正式资产卡。

“可用”必须代表文件已经写入当前主存储，并且后台解析与索引重建成功。配置 S3 时，主存储就是对象存储；未配置 S3 的本地开发环境继续使用本地文件作为兼容回退。任何仅完成浏览器请求、但尚未完成索引的文件都不能显示为“可用”。

## 当前实现与问题

- `POST /api/upload` 读取文件，配置 S3 时等待 `put_object` 成功，然后创建 `queued` 资产并安排后台处理。
- 前端上传完成后只做一次全量刷新并显示全局提示，没有文件级进度、大小或状态过渡。
- `AssetProcessor.process()` 当前先把资产状态写成 `ready`，再重建索引并更新 `chunk_count`。轮询者可能在索引完成前看到 `ready`，因此当前状态不能作为严格的完成信号。
- `Asset` 没有保存文件字节数，正式资产卡也无法稳定显示文件大小。

## 方案选择

采用“前端短时反馈 + 后端真实状态轮询”的组合方案。

不采用同步等待全部处理完成的上传接口，因为 PDF、图片视觉处理和全量索引可能延长请求并触发代理超时。不新增上传任务 SSE，因为现有资产状态接口已经能表达本需求，新增任务协议会扩大实现和维护范围。

前端进度是有上限的阶段反馈，不伪装字节级精确进度：它可以快速推进到 92%，但只有后端资产成为严格意义上的 `ready` 后才能到达 100%。

## 后端设计

### 文件大小

为 `Asset` 增加 `size_bytes: int = 0`：

- 新上传文件使用已经读取的载荷长度写入，不额外读取文件。
- 替换版本也写入新文件的字节数。
- 现有 JSON 资产缺少该字段时迁移为 `0`。
- MySQL 的 `knowledge_assets` 表增加 `size_bytes BIGINT NOT NULL DEFAULT 0`，读取和同步逻辑包含该列。
- `AssetStore.public()` 返回 `size_bytes`，正式资产卡使用统一格式化函数展示。

### 严格的 `ready` 语义

后台处理期间资产保持 `queued` 或 `processing`。处理器完成预览和可选视觉提取后，构造一个仅供本轮索引重建使用的候选资产，但不提前向资产存储发布 `ready`。

索引重建输入由以下内容组成：

- 其他已经 `ready` 且属于当前版本的资产；
- 本轮处理完成、即将发布的当前版本候选资产。

索引重建成功后，处理器读取该资产的片段数量，并以一次最终资产更新写入：

- `status="ready"`；
- `page_count`；
- `chunk_count`；
- `vision_status` 与 `visual_segments`；
- 清空错误信息。

如果主存储读取、预览、视觉处理的必需步骤或索引重建失败，资产进入 `failed`，前端不得显示 100% 或“可用”。可选视觉服务自身失败仍沿用现有行为：资料文本索引可以成功，`vision_status` 单独标记为 `failed`。

### 上传响应

上传接口继续在主存储写入成功、资产记录创建后返回，不等待后台解析。响应包含 `asset_id`、`name`、`size_bytes` 和 `queued` 状态。前端使用 `asset_id` 从项目资产列表查询最终状态。

## 前端设计

### 临时上传记录

在上传区下方维护独立的 `UploadFeedback` 集合，每个文件包含：

- 本地反馈 ID；
- 后端返回后的 `asset_id`；
- 文件名；
- 字节数；
- 0–100 的进度；
- `uploading`、`available` 或 `failed` 状态；
- 可安全展示的失败信息。

选择文件后立即插入记录，初始进度为 8%，状态文案为“上传中”。多文件上传为每个文件保留独立记录，单个失败不移除其他文件的成功反馈。

### 进度与完成判定

进度按以下阶段推进：

1. 文件进入队列：8%。
2. 上传接口返回，证明主存储写入且资产已登记：72%。
3. 轮询期间每 180ms 平滑推进，最高停在 92%。
4. 资产返回 `ready`：立即设置为 100%，状态切换为“可用”。

轮询复用 `/api/assets?project_id=...`，每 500ms 获取当前项目资产。90 秒内没有进入 `ready`，或资产进入 `failed`，反馈切换为“失败”，保留文件名、大小和错误信息，不并入成功资产卡。

### 并入资产卡

成功记录达到 100% 后：

1. 保持“可用”状态 180ms，让用户看见完成结果。
2. 刷新项目资产列表，确保正式卡片来自服务端持久化数据。
3. 临时记录淡出并轻微上移。
4. 对应正式资产卡以淡入和轻微上移归位的方式出现。
5. 从临时集合移除成功记录。

正式资产卡继续显示文件名，并在类型、页数和片段数一行加入格式化文件大小。格式使用 B、KB、MB、GB，最多保留一位小数；历史数据的 `size_bytes=0` 显示“大小未知”。

### 动效与无障碍

只使用 CSS `transform` 和 `opacity`：

- 临时记录进入、退出：160–180ms `ease-out`；
- 进度填充：180ms，通过 `transform: scaleX(...)` 更新，原点位于左侧；
- 正式资产卡完成进入：180ms `ease-out`；
- 位移不超过 6px，避免明显跳动。

在 `@media (prefers-reduced-motion: reduce)` 下：

- 禁用记录和资产卡的位移；
- 取消进度条与透明度过渡；
- 状态、进度数值和并入结果仍完整更新；
- 不依赖动画表达成功或失败。

## 数据流

```text
选择文件
  → 插入“上传中”临时记录
  → POST /api/upload
  → S3 put_object 或本地持久化
  → 创建 queued 资产并返回 asset_id
  → 后台预览/解析/索引
  → 前端轮询资产状态，进度最多到 92%
  → ready 后进度 100% + “可用”
  → 刷新并显示正式资产卡
  → 临时记录退出
```

## 错误处理

- 浏览器到后端上传失败：临时记录切换为“失败”，显示后端安全错误。
- S3 写入失败：上传接口失败，不创建成功资产反馈。
- 后台解析或索引失败：资产状态为 `failed`，反馈不达到 100%。
- 轮询暂时失败：在 90 秒总时限内继续重试，不重复上传文件。
- 用户切换项目：上传记录保留其发起时的项目 ID；成功后只刷新对应项目，避免把资产并入错误项目。

## 测试与验收

### 后端

- 上传创建的资产保存并公开正确的 `size_bytes`。
- JSON 中缺少大小的旧资产可正常读取，并得到 `0`。
- MySQL 同步和加载包含 `size_bytes`。
- 索引重建开始前，对外资产状态仍不是 `ready`。
- 索引成功后才同时公开 `ready` 和最终 `chunk_count`。
- 索引失败时状态为 `failed`。

### 前端

- 选择文件后立即出现带文件名、格式化大小、进度和“上传中”的记录。
- 上传接口返回后进度不会超过 92%，后端 `ready` 前不会显示“可用”。
- `ready` 后显示 100% 和“可用”，然后并入正式资产卡。
- 失败记录不会并入资产卡。
- 样式仅以 `transform`、`opacity` 实现短动效，并包含 `prefers-reduced-motion` 覆盖。
- 多文件各自维护状态，成功与失败互不覆盖。

## 范围边界

- 不增加分片上传、断点续传或字节级浏览器上传进度。
- 不新增 WebSocket、SSE 上传任务或独立任务表。
- 不改变支持的文件类型、最大文件大小、S3 配置方式或知识检索算法。
- 不重构现有大型 `App.tsx`；只提取完成本功能所需的小型类型、格式化函数和展示组件。
