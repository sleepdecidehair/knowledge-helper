# 共享 MySQL 会话同步设计

## 目标

本地与服务器的多个后端进程必须把 MySQL 作为实时会话来源；任一端新建、回答、重命名或删除会话后，另一端下一次读取即可看到一致结果。

## 根因

`ConversationStore` 仅在启动时加载 MySQL 到进程内存，随后 `list()` 和 `get()` 直接读取内存。写入时又会删除两张 MySQL 表并回写整个内存副本，因此不同启动时刻的进程既会显示不同历史，也可能覆盖另一端较新的记录。

## 设计

1. MySQL 已启用时，`list()`、`get()` 和所有修改会话的操作先刷新 MySQL 到内存；连接失败时保留本地 JSON 备份并记录警告。
2. 常规写入只对被修改的单个会话执行 `INSERT ... ON DUPLICATE KEY UPDATE`；该会话的消息在同一事务内按会话 ID 替换。删除操作只删除该会话及其消息。
3. 整表同步只保留给首次 JSON→MySQL 迁移，不再用于日常操作。
4. 本地 JSON 仍是故障备份，不能在已完成迁移后反向覆盖 MySQL。

## 验收

- 两个独立 `ConversationStore` 实例使用同一 MySQL 时，第二个实例的 `list()` / `get()` 能刷新到第一个实例写入的会话。
- 更新一个会话的 SQL 不得包含无条件删除 `conversations` 或 `messages` 全表的语句。
- 删除只影响目标会话。
- 现有 JSON 迁移与完整消息载荷测试继续通过。

## 范围

仅修复本地代码和自动化测试；不部署、不推送、不改动现有 MySQL 数据。
